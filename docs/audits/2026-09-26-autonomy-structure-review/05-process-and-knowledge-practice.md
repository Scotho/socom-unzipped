# Established software-engineering process practice: docs governance, decision records, handoffs, shared-state coordination, small-team sprints, metrics, verification culture

Scope note: all findings below are conventional (non-AI-specific) software-engineering practice, stated concretely so they can be compared against a project carrying ~5,000 lines of governing process docs, 268 numbered "rulings", a 2,500-line STATUS file, per-controller handoff docs, a lock-and-ticket queue for one shared test rig, per-agent git worktrees, pathspec-only commits, pre-commit leak checks, and weekly sprints with a pre-sprint audit.

Source-quality warning: several web searches on these topics (merge-queue contention, "process debt", poka-yoke, ADR anti-patterns, decomp dashboards) returned a high proportion of recent low-authority or apparently AI-generated blog/aggregator content. Where I could not reach a primary source I have said so explicitly and marked the claim as weakly sourced rather than presenting it as established practice.

## Documentation governance: how many docs, how long, who owns them, freshness, deprecation, archival

### Takeaway
The mature-practice consensus is not "write less" but "own, review, date, and delete": every doc has a named owner, lives in source control, is reviewed like code, carries a last-reviewed date that expires, and is either consolidated into a single canonical source or explicitly marked obsolete. Google's own case study is that an unowned, monolithic wiki decayed to ~90% of documents unread and unmaintained — which is the exact failure mode a 5,000-line process corpus plus a 2,500-line STATUS file risks.

### Cited Findings
- Google's rule on ownership: "Documents without owners become stale and difficult to maintain. Clear ownership also makes it easier to handle documentation through existing developer workflows." — [Software Engineering at Google, ch. 10 "Documentation" (2020)](https://abseil.io/resources/swe-book/html/ch10.html)
- The GooWiki failure case: "there were no true owners for documents, many became obsolete"; symptoms included "Monolithic wiki pages with bunches of links (many broken or obsolete)" and "7 to 10 documents … on setting up Borg" of which only some were maintained. At deprecation time, "around 90% of the documents had no views or updates in the previous few months." — [SWE at Google ch. 10](https://abseil.io/resources/swe-book/html/ch10.html)
- Freshness as machinery, not intention: Google docs carry metadata such as `freshness: { owner: 'username' reviewed: '2019-02-27' }`; "Such documents note the last time a document was reviewed, and metadata in the documentation set will send email reminders when the document hasn't been touched in, for example, three months." A "Last reviewed by …" byline is recommended to increase owner accountability. — [SWE at Google ch. 10](https://abseil.io/resources/swe-book/html/ch10.html)
- Docs-as-code checklist (verbatim list items): documentation should "Have internal policies or rules to be followed"; "Be placed under source control"; "Have clear ownership responsible for maintaining the docs"; "Undergo reviews for changes (and change with the code it documents)"; "Have issues tracked, as bugs are tracked in code"; "Be periodically evaluated (tested, in some respect)". The turnaround at Google came because "maintaining documentation became a similar experience to maintaining code: engineers filed bugs, made changes to documents in changelists, sent changes to reviews by experts." — [SWE at Google ch. 10](https://abseil.io/resources/swe-book/html/ch10.html)
- Three distinct review types are recommended for docs: "A technical review, for accuracy"; "An audience review, for clarity"; "A writing review, for consistency". — [SWE at Google ch. 10](https://abseil.io/resources/swe-book/html/ch10.html)
- Deprecation/archival rule: "When a document no longer serves any purpose, either remove it or identify it as obsolete (and, if available, indicate where to go for new information)." And the cheap fallback: "Even for unowned documents, someone adding a note that 'This no longer works!' is more helpful than saying nothing." — [SWE at Google ch. 10](https://abseil.io/resources/swe-book/html/ch10.html)
- Length and single-purpose: "By keeping a document short and clear, you will ensure that it will satisfy both an expert and a novice"; "Writing a short document often requires you to write a longer one (getting all the information down) and then doing an edit pass, removing duplicate information where you can"; "A document should have, in general, a singular purpose, and stick to it." — [SWE at Google ch. 10](https://abseil.io/resources/swe-book/html/ch10.html)
- Single source of truth: "Determine the primary source and consolidate other associated documents into that primary source (or deprecate the duplicates)"; canonical status is helped by short stable links (go/ links) and by "Associating them directly with the code they document by placing them directly under source control and alongside the source code itself." — [SWE at Google ch. 10](https://abseil.io/resources/swe-book/html/ch10.html)
- Google's five document categories: reference documentation (incl. code comments), design documents, tutorials, conceptual documentation, landing pages. — [SWE at Google ch. 10](https://abseil.io/resources/swe-book/html/ch10.html)
- Diátaxis names four and only four documentation needs — tutorials (learning-oriented), how-to guides (task-oriented), technical reference (information-oriented), explanation (understanding-oriented) — positioned in a "systematic relationship"; mixing them confuses readers because each serves a different user need. Diátaxis explicitly sells itself as "light-weight, easy to grasp and straightforward to apply" and as "an active principle of quality … that helps maintainers think effectively about their own work", i.e. incremental improvement rather than a big restructure. — [Diátaxis (diataxis.fr)](https://diataxis.fr/)
- DORA measures internal documentation quality on three attributes — clarity, findability, reliability (eight underlying metrics) — and finds documentation quality acts as a multiplier on every technical practice studied: "documentation quality driving the implementation of every single technical practice we studied." Reported multipliers for teams with above-average vs below-average docs include trunk-based development 1525% vs 36%, continuous integration 750% vs 34%, continuous delivery 656% vs 63%, SRE practices 343% vs 79%, loosely coupled teams 313% vs 46%, version control 278% vs 27%. DORA also concedes the cost: "Documentation needs to be actively created and maintained, which takes work." — [DORA capability: documentation quality](https://dora.dev/capabilities/documentation-quality/)
- Runbook/playbook practice: playbooks "contain high-level instructions on how to respond to automated alerts", explain "the severity and impact of the alert, and include debugging suggestions and possible actions to take"; "In SRE, whenever an alert is created, a corresponding playbook entry is usually created" because playbooks "reduce stress, the mean time to repair (MTTR), and the risk of human error." The staleness warning is explicit: "Details in playbooks go out of date at the same rate as production environment changes." — [Google SRE Workbook, "On-Call" (2018)](https://sre.google/workbook/on-call/)

### Inferences
- The governance pattern that survives is per-document: owner + last-reviewed date + expiry reminder + one purpose. A corpus's total line count is not itself the diagnostic; the diagnostics are (a) how many documents have no named owner, (b) how many have no review date inside the freshness window, (c) how many duplicate a canonical source. A 2,500-line STATUS file almost certainly violates Google's "singular purpose" and "short and clear" guidance and is the structural twin of the "monolithic wiki page" symptom.
- Google's ~3-month freshness reminder and the 90%-unread statistic give a concrete, citable audit test to run against any process corpus: sample documents and check views/edits in the last quarter; anything untouched and unowned is a deletion or archival candidate, not a maintenance candidate.
- DORA's framing matters for the review: reducing doc volume is not the goal — quality on clarity/findability/reliability is, and findability is what a sprawling corpus destroys first.

### Gaps
- I found no authoritative source prescribing a maximum number of process documents or a maximum page/line count per document. Google gives principles ("short and clear", "singular purpose") but no numeric ceiling. Any line-count target in the review will be an inference, not a citation.
- Doc-linting specifics (Vale, markdownlint, link checkers) were not reached with a primary source in this pass; the generic "Be periodically evaluated (tested, in some respect)" line from SWE at Google is the strongest citable hook.

## Decision records: keeping a decision log useful past a few dozen entries; is a monotonic ruling list an anti-pattern?

### Takeaway
ADR practice deliberately uses a monotonically growing, append-only, immutable numbered log — but it survives scale only because each record has a status field, a supersede pointer, and a maintained index, and because ADRs are scoped to *architecturally significant* decisions rather than to every incident. A growing list is therefore not inherently an anti-pattern; an unindexed, statusless, unscoped list is.

### Cited Findings
- Nygard's original format: Title (short noun phrase), Context (value-neutral description of the forces at play), Decision (stated as "We will…"), Consequences (positive and negative). Records are "numbered sequentially and monotonically", numbers are never reused, and each ADR is treated "as if it is a conversation with a future developer", kept to one or two pages in lightweight markup. — [Michael Nygard, "Documenting Architecture Decisions" (2011)](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions)
- Immutability plus supersede, not deletion or editing: "If a decision is reversed, we will keep the old one around, but mark it as superseded." Status can be "deprecated" or "superseded" with a reference to the replacement. — [Nygard (2011)](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions)
- Scoping rule: an Architectural Decision is "a justified design choice that addresses a functional or non-functional requirement that is architecturally significant"; an ADR captures "a single AD and its rationale"; and "the collection of ADRs created and maintained in a project constitute its decision log". The site frames ADRs as part of Architectural Knowledge Management. — [adr.github.io (ADR organization)](https://adr.github.io/)
- MADR (the most widely used modern template) carries an explicit machine-checkable status vocabulary — "proposed | rejected | accepted | deprecated | … | superseded by ADR-0123" — so a supersede chain is traversable forward from the old record. — [About MADR](https://adr.github.io/madr/)
- Weakly sourced (secondary blog, treat as practitioner opinion, not established finding): the common operational pattern is an index table in a `README.md` in the ADR directory holding number, title and status for every accepted ADR; superseding means adding a "Superseded by ADR-000X" line to the old record and never editing its body; the named failure modes are staleness (the decision is a point in time, the code drifts) and conflating RFCs/ADRs/design docs, which produces the "we have 200 ADRs, and nobody reads them" complaint. — [hidekazu-konishi.com, "Architecture Decision Records: Templates and Operational Patterns for Teams That Actually Maintain Them"](https://hidekazu-konishi.com/entry/architecture_decision_records_templates_and_operations.html)
- Alerting analogue for "every incident adds a record": SRE creates a playbook entry per alert — a deliberately 1:1 growth rule — but pairs it with the acknowledgement that entries decay at the rate the system changes. — [SRE Workbook, On-Call](https://sre.google/workbook/on-call/)

### Inferences
- The defensible test for a 268-entry ruling list is not its length but: does every entry have a status (active / superseded-by / retired)? Is there a generated index? Is each entry architecturally significant, or are operational one-offs (which belong in a runbook or a lint rule) being minted as permanent rulings? ADR practice would classify the latter as category confusion, not as a decision log problem.
- ADR practice gives a direct precedent for *not* rewriting history: superseding beats editing. That argues against compacting a ruling list by deletion, and for adding status + index + tags so the active subset is small even when the archive is large.
- The one-or-two-page-per-record norm plus "single AD per record" implies the right unit of compaction is "collapse many rulings into one governing rule with a supersede pointer", not "shorten each ruling".

### Gaps
- I did not find a primary, authoritative source stating that a large ADR corpus is an anti-pattern or prescribing a cap. The "200 ADRs and nobody reads them" phrasing comes from a secondary blog and should be quoted as practitioner opinion only.
- adr.github.io's homepage does not itself give indexing or scaling guidance (confirmed by fetch); tooling pages (adr-tools, Log4brains) exist but were not fetched, so tool-level index generation is unverified here.

## Handoffs and durable memory: what belongs in a handoff vs a runbook vs a status page; bus factor

### Takeaway
SRE handoff practice is a short, per-shift, disposable artifact — a handoff email read at the start of the next shift — explicitly separate from playbooks (durable, per-alert, procedural) and from incident postmortems (durable, per-event, analytical). Durable knowledge belongs in the playbook; transient state belongs in the handoff; the handoff is not supposed to accumulate.

### Cited Findings
- The handoff ritual: "At the start of each shift, the on-call engineer reads the handoff from the previous shift"; "At the end of the shift, the on-call engineer sends a handoff email to the next engineer on-call." Evernote's case study pairs "a well-oiled handoff procedure, alongside a morning review of incidents at a daily stand-up." — [Google SRE Workbook, On-Call](https://sre.google/workbook/on-call/)
- Separation of concerns: playbooks are the durable procedural artifact ("high-level instructions on how to respond to automated alerts", severity/impact, debugging suggestions, mitigation actions), created 1:1 with alerts, and teams must explicitly decide "whether playbooks should be general references or detailed step-by-step procedures, then establish processes to keep them synchronized with system changes." — [SRE Workbook, On-Call](https://sre.google/workbook/on-call/)
- Postmortems are the third, distinct artifact, with pre-agreed triggers (user-visible downtime beyond a threshold, data loss of any kind, on-call intervention such as rollback or traffic rerouting, resolution time beyond a threshold, monitoring failure requiring manual discovery): "It is important to define postmortem criteria before an incident occurs so that everyone knows when a postmortem is necessary." — [Google SRE Book, "Postmortem Culture" (2016)](https://sre.google/sre-book/postmortem-culture/)
- Postmortem hygiene that keeps the corpus useful: senior-engineer draft review covering data collection, impact assessment, root-cause depth, "action plan appropriateness and bug fix priorities", and stakeholder communication; then broader sharing; then the norm "No Postmortem Left Unreviewed" via regular review sessions that close discussion and finalize the document; then storage in a searchable repository. — [SRE Book, Postmortem Culture](https://sre.google/sre-book/postmortem-culture/)
- Blamelessness as the mechanism that keeps handoffs and postmortems honest: "Blameless postmortems are a tenet of SRE culture"; "Removing blame from a postmortem gives people the confidence to escalate issues without fear." The contrast drawn is between finger-pointing ("We need to rewrite the entire complicated backend system!") and constructive framing of the same action item. — [SRE Book, Postmortem Culture](https://sre.google/sre-book/postmortem-culture/)
- Bus factor is defined as "the minimal number of engineers that have to be hit by a bus for a project to be stalled"; a survey of 269 engineers found the bus factor "is perceived as an important problem in collective development", and the paper proposes a multimodal estimation algorithm using code-review and meeting data alongside VCS data. — [Jabrayilzade et al., "Bus Factor In Practice", ICSE-SEIP 2022 (arXiv preprint)](https://arxiv.org/pdf/2202.01523); [ACM DL entry](https://dl.acm.org/doi/10.1145/3510457.3513082)
- Knowledge-concentration measurement: Degree of Knowledge (DOK) combines Degree of Authorship and Degree of Interest to track ownership distribution; visualization of "knowledge islands" is proposed to surface concentration. — [Knowledge Islands: Visualizing Developers Knowledge Concentration (arXiv 2408.08733)](https://arxiv.org/pdf/2408.08733)
- Google's ownership guidance for docs is the doc-side equivalent of bus-factor mitigation: unowned docs go stale, and the fix is named owners plus review bylines. — [SWE at Google ch. 10](https://abseil.io/resources/swe-book/html/ch10.html)

### Inferences
- The three-artifact split maps cleanly onto the project under review: a per-controller HANDOFF doc should be short and transient (current in-flight state, open risks, what the next controller must do first) and should *not* be the place durable procedure accumulates; durable procedure belongs in a runbook-equivalent (scripts + their docs), and durable narrative belongs in dated, reviewed records. A handoff that grows monotonically is doing the runbook's job.
- A 2,500-line STATUS file is functionally a status page plus a handoff plus an archive fused together; SRE practice separates the three precisely because their lifetimes differ (minutes/shift, quarters, forever).
- Bus-factor literature supplies the strongest *justification* for a documentation-heavy autonomous project, and also the cheap measurement: per-path authorship concentration from git. That is the metric to cite rather than "we need more docs".

### Gaps
- I did not find primary literature specifically on written handoff documents in solo/tiny-team settings (as opposed to rotating on-call shifts), so the transfer of SRE handoff norms to a one-owner project is an inference.
- The requested Brooks's law / Conway's law angle was not researched in this pass (search budget went to the higher-value primary sources); no citations here for either. Another researcher or the writer should source those separately if the report needs them.

## Coordination on shared resources: merge queues, trunk-based development, branch lifetime, one-owner-per-path

### Takeaway
The conventional answer to contention on a single integration point is not to remove the serialization but to make it cheap: a merge queue serializes validation against the real post-merge state, batches candidates so the expensive test resource runs once per batch instead of once per change, and evicts failures automatically. Branch lifetime is capped in days, not weeks, and branches are single-owner by convention.

### Cited Findings
- Merge queue purpose (verbatim): it "help[s] increase velocity by automating pull request merges into a busy branch and ensuring the branch is never broken by incompatible changes", and is "particularly useful on branches that have a relatively high number of pull requests merging each day from many different users." — [GitHub Docs, "Managing a merge queue"](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue)
- Mechanism: the queue builds temporary branches combining the target branch's latest code, the PR's changes, and the changes of PRs ahead of it in the queue; it requires "all required status checks when applied to the latest version of the target branch" before merging; failed checks automatically remove the offending PR from the queue. — [GitHub Docs, merge queue](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue)
- Batch-size control is an explicit knob: administrators set minimum and maximum group sizes (1–100 PRs); the maximum limits how many changes deploy together, the minimum plus a timeout lets small batches through when the queue is not full. — [GitHub Docs, merge queue](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue)
- Branch lifetime, with a number: "the branch should only last a couple of days. Any longer than two days, and there is a risk of the branch becoming a long-lived feature branch (the antithesis of trunk-based development)." — [trunkbaseddevelopment.com, "Short-Lived Feature Branches"](https://trunkbaseddevelopment.com/short-lived-feature-branches/)
- One owner per branch, verbatim: "the developer count should stay at one (or two if pair-programming). These short-lived feature branches are not shared within a team for general development activity." Sharing is permitted for code review, not for concurrent production-code work. Before integration, the developer merges from trunk into the branch, then pushes back — a two-phase merge. — [trunkbaseddevelopment.com](https://trunkbaseddevelopment.com/short-lived-feature-branches/)
- Per-path ownership as an enforced convention: CODEOWNERS means "Code owners are automatically requested for review when someone opens a pull request that modifies code that they own"; patterns are gitignore-like, "the last matching pattern takes the most precedence", and under branch protection "an approval from *any* of the owners is sufficient to meet this requirement". Limits: the file must be under 3 MB and negation (`!`) and character-range (`[ ]`) patterns are unsupported; the file must live in `.github/`, the repo root, or `docs/`, checked in that order. — [GitHub Docs, "About code owners"](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners)
- Documentation quality has the largest measured multiplier on trunk-based development of any practice DORA studied (1525% with above-average docs vs 36% with below-average) — i.e. the coordination convention and the docs that describe it are coupled. — [DORA documentation quality](https://dora.dev/capabilities/documentation-quality/)
- Weakly sourced (vendor blog; useful for the history of speculative merging, not for numbers): speculative merging — testing queued changes as the group that would land and merging what passed together — originated with Zuul in OpenStack and appears in Bors, Prow/Tide, Mergify, Graphite, Aviator and GitHub's merge queue. — [Mergify, "The Origin Story of Merge Queues"](https://mergify.com/blog/the-origin-story-of-merge-queues); [Aviator, "What's a bors, and Why (Don't) You Want It?"](https://www.aviator.co/blog/what-is-bors/)

### Inferences
- A lock-and-ticket queue for one shared test rig is the same shape as a merge queue's serialized validation stage, minus two of the merge queue's three cost-savers: batching (validate N candidates in one rig run) and automatic eviction on failure. Those are the concrete upgrades the literature suggests, along with a bounded max batch size so a bad batch is cheap to bisect.
- Per-agent worktrees are the local analogue of short-lived single-owner feature branches; the citable discipline is the two-day lifetime cap and the merge-from-trunk-before-push step, both of which are checkable from git (`git log` age of the branch point).
- Pathspec-only commits and a "never stage a file a running agent is editing" rule are an informal CODEOWNERS: the literature's version makes ownership declarative and machine-enforced (a file that declares its owner) rather than a discipline the committer must remember — which is the poka-yoke point below.

### Gaps
- I found no primary source measuring the throughput cost of a *single* shared hardware test resource (as opposed to elastic CI), nor established guidance on lock/ticket queue design for one rig. The merge-queue analogy is my inference.
- Accelerate's own statistical results on branch lifetime and integration frequency were not retrieved from a primary source in this pass; trunkbaseddevelopment.com's two-day rule is the concrete citable number. DORA's throughput metrics (below) are the measurable proxy.

## Sprints, retros and process debt for tiny teams; rules vs guardrails

### Takeaway
The small-team literature converges on fixed time boxes with a hard stop, an explicit appetite instead of an estimate, no accumulating backlog, and a strict WIP limit — and on retrospectives that produce few, owned, time-boxed changes. The named failure mode is exactly the one a 268-ruling list suggests: each retrospective or incident minting another item until the set has no priority at all. The structural answer from lean practice is to convert rules into guardrails that make the wrong action hard or impossible rather than forbidden in prose.

### Cited Findings
- Shape Up's time box and its rationale: six-week cycles, chosen because six weeks is "long enough to finish something meaningful and short enough to feel the deadline from the beginning", followed by a two-week cool-down for ad-hoc work and bug fixes, during which the betting table meets. — [Shape Up, Basecamp (2019)](https://basecamp.com/shapeup/webbook)
- Appetite instead of estimate: leaders set "the amount of time they want to invest" before work begins; a bet comes with no interruptions and an expectation to finish. — [Shape Up](https://basecamp.com/shapeup/webbook), [ch. 8 "The Betting Table"](https://basecamp.com/shapeup/2.2-chapter-08)
- No backlog: Shape Up replaces backlogs with decentralized lists of potential bets, on the theory that important ideas resurface naturally rather than languishing in queues. — [Shape Up](https://basecamp.com/shapeup/webbook)
- The circuit breaker: projects that do not ship within one cycle are cancelled by default rather than extended. Progress is tracked on a hill chart (unknown → known → done) instead of by estimates; work is divided into "scopes" — independently buildable parts organized by structure rather than by person. — [Shape Up](https://basecamp.com/shapeup/webbook)
- Kanban's three practices are defining/visualizing a workflow, actively managing items in it, and improving it; WIP control is mandatory but its representation is free: "Kanban system members must explicitly control the number of work items in a workflow from started to finished. That control can be represented on a Kanban board in any way that Kanban system members deem appropriate", operating "neither above nor below the agreed upon control." — [Kanban Guide (kanbanguides.org)](https://kanbanguides.org/english/)
- Pull rule: "Kanban system members should start work on an item (pull or select) only when there is a clear signal that there is capacity to do so. When WIP drops below the control set in the DoW, that can be a signal to select new work." — [Kanban Guide](https://kanbanguides.org/english/)
- Postmortem action items must be owned, prioritized and reviewed — the draft review explicitly checks "action plan appropriateness and bug fix priorities", and the "No Postmortem Left Unreviewed" norm exists to close out documents rather than let them pile up open. — [SRE Book, Postmortem Culture](https://sre.google/sre-book/postmortem-culture/)
- Poka-yoke (Shigeo Shingo's mistake-proofing) applied to software, in three levels: design-level prevention — "It should take less code to use the API properly then to unintentionally misuse it"; runtime safeguards — components must fail clearly and unambiguously rather than proceeding dangerously or dying silently; and testing-level detection via inexpensive, repeatable, reliable checks at the source. The framing is that quality should be "caused, not controlled". — [Gojko Adzic, "The Poka-Yoke principle and how to write better software" (2007)](https://gojko.net/2007/05/09/the-poka-yoke-principle-and-how-to-write-better-software/)
- Poka-yoke's general definition: "any mechanism in a process that helps an equipment operator avoid mistakes and defects by preventing, correcting, or drawing attention to human errors as they occur." — [Wikipedia, "Poka-yoke"](https://en.wikipedia.org/wiki/Poka-yoke)
- Weakly sourced (practitioner/vendor guides on retrospective anti-patterns; useful for naming the failure mode, not as research): "Creating too many goals retro after retro leads to a backlog of action items and to-do lists that are constantly getting reprioritized before eventually being dropped"; and "when you have too many top priorities, you effectively have no top priorities". Companion anti-patterns: vague/unmeasurable action items ("improve communication"), action items accepted with no owner, and no follow-up check on prior items. Prescribed fix: SMART action items (specific, measurable, achievable, relevant, time-boxed). — [Retrium, "Retrospective Anti-Patterns"](https://www.retrium.com/ultimate-guide-to-agile-retrospectives/retrospective-anti-patterns); [Scrum.org, "21 Sprint Retrospective Anti-Patterns"](https://www.scrum.org/resources/blog/21-sprint-retrospective-anti-patterns); [Easy Agile, "Why Retrospectives Fail"](https://www.easyagile.com/blog/improve-sprint-retrospective-action-items)

### Inferences
- The strongest citable argument against a monotonically growing prose rulebook is the guardrail argument, not a length argument: a rule that exists only in a document depends on the actor remembering it, whereas a pre-commit hook, a CODEOWNERS entry, a lock-acquisition script that refuses a bare take, or a test that fails loudly is poka-yoke — it removes the need for the rule to be read. The project already has three instances of this (pre-commit leak checks, the ticketed lock that refuses a bare take while queued, the chain's before/after git-status snapshot); the review's structural recommendation is to convert prose rulings into such devices wherever a ruling is mechanically checkable, and to retire the prose when the device lands.
- Weekly sprints with a pre-sprint audit are a shorter Shape Up cycle with the cool-down folded into the audit. Two Shape Up devices look directly transferable and are currently absent: an explicit appetite per task (a time budget, so the work is scoped to the box rather than the box extended to the work) and a circuit breaker (unfinished work is cancelled and re-bet, not rolled forward indefinitely).
- Kanban's four flow metrics give a cheaper health readout for a tiny team than sprint ceremonies do, and WIP-limit discipline is the direct check on running several agents plus one shared rig.

### Gaps
- "Process debt" is not an established, well-defined term in the primary literature I reached; the closest sourced concept is the retrospective anti-pattern of accumulating unowned action items, and it comes from practitioner blogs rather than research. The report should not present "process debt" as a named research finding.
- Shape Up chapter-level URLs beyond ch. 8 were not individually verified; cite the webbook root.

## Metrics: DORA four keys, reliability, rework, flow efficiency, WIP age — and cheap instrumentation from git

### Takeaway
DORA now publishes five delivery metrics (three throughput, two instability) and, as of the 2025 report, has abandoned the elite/high/medium/low clustering in favour of team archetypes — so quoting "elite thresholds" needs a year attached. For a tiny team, the cheap instrumentation story is git timestamps plus Kanban's four flow metrics (WIP, throughput, cycle time, work item age), all derivable from commit/branch history without any tooling.

### Cited Findings
- DORA's current five metrics, verbatim definitions. Throughput: change lead time — "The amount of time it takes for a change to go from committed to version control to deployed in production"; deployment frequency — "The number of deployments over a given period or the time between deployments"; failed deployment recovery time — "The time it takes to recover from a deployment that fails and requires immediate intervention". Instability: change fail rate — "The ratio of deployments that require immediate intervention following a deployment"; deployment rework rate — "The ratio of deployments that are unplanned but happen as a result of an incident in production". The page states the metrics have "shift[ed] from the original four keys to the current five-metric model". — [DORA, "DORA's software delivery metrics: the four keys"](https://dora.dev/guides/dora-metrics-four-keys/)
- DORA's own advice on cheap measurement is to start with conversations and the DORA Quick Check rather than building integrations. — [DORA four keys guide](https://dora.dev/guides/dora-metrics-four-keys/)
- Kanban's four mandatory flow metrics, verbatim: WIP — "The number of work items started but not finished"; throughput — "The number of work items finished per unit of time. Note the measurement of throughput is the exact count of work items"; cycle time — "The elapsed time between when a work item started and when a work item finished"; work item age — "The elapsed time between when a work item started and the current date". — [Kanban Guide](https://kanbanguides.org/english/)
- 2024 DORA report findings relevant to batch size and stability: "AI adoption significantly increases individual productivity, flow, and job satisfaction. However, it also negatively impacts software delivery stability and throughput", with "small batch sizes" and "robust testing" remaining crucial; and "Unstable organizational priorities cause meaningful decreases in productivity and substantial increases in burnout." — [DORA 2024 report landing page](https://dora.dev/research/2024/dora-report/)
- Secondary but specific on thresholds (vendor guide, source year not stated on the page — flag the year uncertainty): Elite = multiple deploys per day, lead time < 1 day, change failure rate 0–15%, MTTR < 1 hour; High = daily–weekly, 1 day–1 week, 16–30%, < 1 day; Medium = weekly–monthly, 1 week–1 month, 16–30%, 1 day–1 week; Low = monthly–biannually, 1–6 months, 46–60%, 1 week–1 month. Same source on cheap instrumentation: "Deployment frequency comes from Git or CI/CD tools like GitLab CI or Jenkins. Lead time comes from timestamps across Jira or Git", and "GitHub and GitLab both ship built-in DORA dashboards now, which lowers the setup cost considerably." — [DX, "DORA metrics: the complete guide"](https://getdx.com/blog/dora-metrics/)
- The 2025 report restructured the framework: secondary reports state it "moved away from low / medium / high / elite clusters entirely, introducing seven archetypes instead", defined by the intersection of delivery performance with human factors such as burnout and organizational friction, and that change failure rate "consistently behaved like an outlier and didn't load cleanly with the other metrics". One secondary source reports the 2025 ideal CFR for top performance as 0–2%, with 16.7% of respondents at that level. Treat these as secondary until the report PDF is read. — [RedMonk, "DORA 2025: Measuring Software Delivery After AI"](https://redmonk.com/rstephens/2025/12/18/dora2025/); [CI/CD Watch, "DORA Metrics Benchmarks 2026"](https://cicd.watch/blog/dora-metrics-benchmarks-2026)
- Bus-factor/knowledge metrics computable from repository history: DOK (Degree of Authorship + Degree of Interest) for ownership distribution, and multimodal bus-factor estimation from VCS plus code-review data. — [Knowledge Islands (arXiv 2408.08733)](https://arxiv.org/pdf/2408.08733); [Bus Factor In Practice (arXiv 2202.01523)](https://arxiv.org/pdf/2202.01523)

### Inferences
- For this project the four keys translate with almost no tooling: deployment frequency = merges to the sprint/main branch (or tagged builds); change lead time = first commit on an agent branch → merge timestamp; change failure rate = merges followed by a fix-round or revert commit (the project's own "fix round" language is already a CFR proxy); failed-deployment recovery time = time from the breaking merge to the fix merge. All four are `git log` queries.
- Rework rate is the single most diagnostic metric for a review-gated autonomous pipeline: the project's visible pattern of "review PASS after one fix round" is exactly a change-fail/rework signal, and counting fix rounds per task over sprints is a cheap trend line.
- Work item age is the metric most likely to expose a lock-bound shared rig: an agent blocked on the rig accumulates age without accumulating throughput, which a per-ticket wait time from the lock queue would measure directly.
- Because DORA dropped the four-tier clusters in 2025, the report should present thresholds as "2023/2024-era clusters" and avoid implying current DORA endorses them.

### Gaps
- I could not retrieve the official threshold table from a dora.dev or report-PDF URL; the numbers above are from a vendor guide that does not state its source year, and I could not confirm the 2025 "0–2% CFR" figure or the seven archetypes from a primary DORA source. Flag as needing verification against the report PDF.
- "Flow efficiency" (active time ÷ total elapsed time) is not defined in the Kanban Guide and I did not reach a primary source for it in this pass; the Kanban Guide's four metrics do not include it. Do not attribute flow efficiency to the Kanban Guide.

## Verification culture: evidence-based claims, and how decompilation/emulation projects gate regressions

### Takeaway
The closest professional analogues to this project — emulator and matching-decompilation projects — do not rely on reviewer judgment; they rely on mechanical, high-volume differential testing against a captured reference (GPU command dumps replayed and image-diffed; every previously decompiled file re-decompiled on every build and compared to a checked-in reference) plus a public percentage dashboard as the progress signal. Evidence is an artifact (a diff, an HTML report with pictures, a percentage), not a claim.

### Cited Findings
- PCSX2's GS dump runner is a differential image-diff harness: "The GS dump runner is designed to automatically run and compare a large number of GS dumps and output any differences found w/pictures." It gives "the difference in texture uploads, swizzles, readbacks, and can do frame-by-frame analysis", and the workflow is two Python scripts — `test_run_dumps.py` to produce results for a build, `test_check_dumps.py` to compare baseline vs modified and log differing frames "to both terminal and an HTML file"; `-parallel 4` is recommended. Scale: "Every GS change usually gets tested by 2000+ different scenes in games." — [PCSX2 wiki, "How to use the GS Dump Runner"](https://github.com/PCSX2/pcsx2/wiki/How-to-use-the-GS-Dump-Runner); [PCSX2 docs, GS Dump Runner](https://pcsx2.net/docs/advanced/gsdumprunner/)
- OpenGOAL's regression gate is total re-derivation on every build: "Every build to the repository re-decompiles and compiles every file ever decompiled as a regression test", and adding a newly decompiled file to the gate means copying its `*_disasm.gc` output into `./test/decompiler/reference/jak2/…` renamed `_REF`. The suite runs as an `offline-test` binary, is shardable across threads, and is wired into CI (including handling for untrusted-author PRs). — [OpenGOAL docs, "Decompiling: Getting Started"](https://opengoal.dev/docs/developing/decompiling/getting_started/); [jak-project Taskfile.yml](https://github.com/open-goal/jak-project/blob/master/Taskfile.yml)
- Public progress dashboards are the norm for matching projects: decomp.dev aggregates hundreds of projects across PlayStation, N64, GameCube, DS, Wii, Switch, 3DS, Xbox and GBA, showing decompilation percentage, fully-linked percentage, and code statistics (total vs matched code volume), with per-project "Updated [time] in commit [hash]" provenance from GitHub integration. — [decomp.dev projects](https://decomp.dev/projects); [decomp.me FAQ](https://www.decomp.me/faq)
- Matching decompilation's definition of done is byte-identical output: projects "attempt to write source code (C, C++) that compiles to the same binary as the original", and the permuter exists to close the gap between a near-match and an exact match by permuting C forms until register allocation and instruction ordering agree, scoring candidate outputs (`output-<score>-…`). — [decomp.dev](https://decomp.dev/projects); [decomp.me](https://www.decomp.me/)
- Static recompilation (the technique this project uses) is documented by N64Recomp as literal instruction-by-instruction translation — "accepts a list of symbols and metadata alongside the binary with the goal of splitting the input binary into functions that are each individually recompiled into C code that can be compiled for any platform", e.g. `addiu $r4, $r4, 0x20` becoming `ctx->r4 = ADD32(ctx->r4, 0X20);` — with TOML config to "optionally stub out specific functions, skip recompilation of specific functions, and patch single instructions in the target binary", and a single-file output mode where compiled patches replace original functions via linker precedence. Notably, the README documents **no** automated validation or comparison against the original binary; it only notes the recompiler "has mostly been tested on binaries built with old MIPS compilers". — [N64Recomp README](https://github.com/N64Recomp/N64Recomp)
- The docs-side equivalent of evidence-as-artifact: Google requires docs to "Undergo reviews for changes" and to "Be periodically evaluated (tested, in some respect)", and requires a technical review "for accuracy" by a subject-matter expert. — [SWE at Google ch. 10](https://abseil.io/resources/swe-book/html/ch10.html)
- Postmortem review as evidence discipline: draft review explicitly checks whether "Key incident data" was collected and whether impact assessment and root-cause depth are complete before the document is finalized. — [SRE Book, Postmortem Culture](https://sre.google/sre-book/postmortem-culture/)

### Inferences
- The decisive structural difference between this project and its analogues is *where* the verification effort sits. PCSX2 and OpenGOAL invest in one high-volume mechanical differential gate (2000+ scenes; re-decompile everything every build) and spend very little prose on rules; a process corpus of 5,000 lines plus 268 rulings plus per-task review rounds is spending the same effort on human-legible governance instead. The citable recommendation is to move effort from prose rules to a captured-reference differential harness (e.g. frame/GS-trace capture replayed and image-diffed on every build; recompiler output re-derived and diffed against a checked-in reference) so that "RED n / GREEN n" claims become artifacts rather than assertions.
- Static recompilation projects have a *weaker* automatic correctness oracle than matching decompilation (there is no byte-identical target), which raises rather than lowers the value of a golden-reference replay harness and a published percentage/coverage dashboard. N64Recomp's silence on validation is evidence that this is an underdeveloped area in the field, not evidence that it is unnecessary.
- A public percentage dashboard (decomp.dev-style) is the field's answer to "what is our health signal", and it is the natural pairing with DORA-style rework counts for this project: coverage/parity trend plus fix-rounds-per-task.

- I found no primary source describing an automated *behavioural* parity harness (original hardware/emulator vs recompiled build) for a PS2 static recompilation; if the report needs that, it should be stated as an absence in the published literature rather than sourced.
